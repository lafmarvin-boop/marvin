## 3. À décider par toi

**🔴 Critique — `push-notify.js` (tout le fichier). Persistant, aucune information nouvelle.** Toujours aucune authentification : n'importe qui peut POSTer un titre/message/URL de notification push vers un ou tous les écoutants. Toujours pas corrigé pour la même raison qu'hier (appelée en interne sans identité par `chat-send.js`/`free-session.js`/`chat-start.js` ; nécessiterait un secret partagé entre fonctions internes).

**🔴 Critique (mitigé) — `monthly-accounting.js:574-575`. Persistant, code inchangé.** La fenêtre de contournement (`next_run` seul, sans mot de passe admin, mais seulement le 26 du mois UTC) existe toujours. `accounting-run.js`, ajouté depuis hier pour le bouton admin, ne change rien à ce point : il s'ajoute à `monthly-accounting.js`, il ne le remplace pas.

**🟠 Haute — `change-password.js`, `cancel-subscription.js:44-50`, `subscriber-session.js:43-49`. Persistant, périmètre élargi.** Le finding d'hier portait sur `change-password.js` seul ; en le revérifiant j'ai constaté que **la même faille de fenêtre de course touche aussi `cancel-subscription.js` et `subscriber-session.js`** — les trois fonctions partagent le même motif `if (!byToken && sub.password_hash && sub.password_salt)` : tant qu'aucun hash n'existe pour un compte abonné, l'email seul suffit à changer le mot de passe, résilier l'abonnement Stripe, ou démarrer une session gratuite en son nom. La fenêtre reste celle identifiée hier : `create-subscription.js` crée l'abonnement Stripe (ligne 103) avant d'écrire le hash dans Supabase (ligne 126), et `stripe-webhook.js` (`upsertSubscriber`, sans hash) peut upserter la même ligne entre les deux. Non corrigé : touche l'ordre d'écriture entre deux flux de paiement Stripe.

**🟡 Moyenne — `visitor-push-notify.js`. Persistant, inchangé.** Aucune authentification, contenu de notification fixe (pas d'injection) : risque limité au spam de notification visiteur.

**🟡 Moyenne — `end-session.js` / `submit-rating.js` / `report-slow-agent.js`. Persistant, un fichier de plus identifié.** Ces trois fonctions utilisent un identifiant Stripe/session (UUID) comme secret implicite sans mot de passe. Nouveau depuis hier : `report-slow-agent.js` rembourse un paiement réel sur la seule preuve d'un `paymentId` connu (`pi_...`) — cohérent avec le reste de l'architecture visiteur, mais si ce payment_intent fuite (Referer, historique), un tiers peut déclencher un remboursement sur un paiement qui n'est pas le sien. Pas de correctif local évident sans changer le modèle d'accès visiteur.

**🟡 Moyenne — Abus/spam sans limite. Persistant.** `chat-request.js`, `notify-admin.js`, `submit-manual-review.js`, `track-chat.js` : toujours aucune limite de fréquence (nécessite une nouvelle table Supabase, exclu explicitement).

**🟡 Moyenne — `stripe-webhook.js`. Persistant.** Toujours aucune vérification d'idempotence sur `webhookEvent.id`. Impact limité (PATCH/upsert idempotents).

**🟢 Basse (RGPD) — `free_trial_ips`. Persistant.** Toujours aucune purge (contrairement à `visits`, 30 jours). Probablement volontaire (anti-abus offre gratuite) : à trancher.
